## Outcome

Build a polished responsive web app named **Lyrics Dictation** for people to memorize and write an entire song’s lyrics from memory in one free-form editor. A user imports lyrics, chooses a song, and types freely in a large multiline writing surface while the app continuously aligns the draft with the expected lyrics and marks correct, incorrect/extra, and missing text in real time. It must support Chinese and English, accept only user-supplied lyric text or lyric files, synchronize data in the cloud without accounts, and be deployable on Cloudflare.

The repository is implementation-complete only when the application, database migrations, automated tests, security/privacy protections, documentation, and Cloudflare deployment configuration all work together and the independent adversarial review described below has passed. Locally verified deployment configuration is not the same as a remotely deployed production service.

## Product scope

### 1. Languages and interface

- Ship complete Simplified Chinese (`zh-CN`) and English (`en`) UI translations.
- On first visit map `zh`, `zh-CN`, `zh-SG`, and `zh-Hans` browser preferences to `zh-CN`; map any `en-*` preference to `en`; otherwise fall back to `en`. Let the user switch language at any time. A manual choice wins over browser detection, is persisted immediately in local storage for startup, and is synchronized to the anonymous D1 settings record once an identity exists. On later loads a valid server setting is authoritative and refreshes local storage.
- All user-visible application strings, validation messages, empty/error/loading states, document title/description, not-found pages, server-error presentation, and accessibility labels must go through the localization system. Set `<html lang>` correctly. Tests must fail if either locale is missing required keys.
- User-entered song titles, artists, and lyrics are content and must never be translated automatically.
- Provide a coherent, restrained visual system with excellent typography for both Latin and CJK text. Support phone, tablet, and desktop layouts down to 360 px width. Avoid generic template styling and ornamental UI that does not aid study.

### 2. Lyric import and library

- The only lyric inputs are:
  1. pasting plain text or LRC into a text area; and
  2. uploading a local `.txt` or `.lrc` file.
- Do not integrate music, audio playback, microphones, streaming services, lyric providers, scraping, URLs, or third-party content catalogs.
- Decode UTF-8 strictly, remove one leading BOM, and normalize CRLF/CR to LF for the editable stored source. Recognize LRC timestamps in common `[mm:ss]`, `[mm:ss.xx]`, and `[mm:ss.xxx]` forms. Recognize only metadata tags `ar`, `ti`, `al`, `by`, `offset`, `re`, `ve`, and `length` case-insensitively; use `ar` and `ti` only to prefill editable artist/title, and omit recognized metadata-only lines from study content. Preserve unknown or malformed bracketed text as lyrics rather than silently discarding it.
- LRC ordering is normative: if every non-metadata, non-blank lyric line has at least one valid timestamp, expand every timestamp into a distinct lyric occurrence, sort occurrences by numeric timestamp, preserve source order for ties, and do not deduplicate repeats. If any studyable line is untimed, ignore all timestamps for ordering, preserve source-line order, and include each source line once after stripping its valid leading timestamp sequence. Preserve blank lines in the editable source but exclude them from sessions. Let the user review and edit parsed title, artist, and source before saving, and regenerate study lines from the edited source.
- Enforce shared client/server limits from one documented configuration: uploaded UTF-8 bytes at most 256 KiB; decoded source at most 100,000 Unicode scalar values; at most 2,000 source lines; each source line at most 2,000 Unicode scalar values; title and artist each at most 200 Unicode scalar values. Apply the same 256 KiB and 100,000-scalar limits independently to an edited dictation draft. Reject or truncate nothing silently: prevent further input or a paste that would exceed the draft limit while preserving the prior draft and selection, and show a localized actionable message. Reject unsupported extensions, invalid UTF-8, and songs with zero non-blank studyable lines. The server is authoritative. Test every boundary and one-over-boundary case and show localized actionable errors. Treat filenames and contents as untrusted input.
- Provide a personal library with create/import, view, edit, search, sort, and delete. A destructive delete requires confirmation and must remove dependent study data transactionally.
- Store normalized lyric lines while preserving the user’s original text for future editing. Never include sample copyrighted lyrics; tests and demos must use short original or public-domain fixture text.

### 3. Study and dictation flow

- A song detail view has a **Study** view that shows the complete lyrics and a **Start dictation** action. Starting dictation hides the expected lyrics; do not place the answer beside, behind, or faintly inside the writing surface.
- The dictation screen is a calm, document-like workspace dominated by one large multiline editor. The user can type continuously, insert and delete at any position, select text, paste plain text, and create or remove line breaks. Normal browser editing expectations—including pointer placement, keyboard navigation, selection, clipboard operations, undo/redo, mobile editing, and Chinese/English IME composition—must work. It is not a sequence of line-sized inputs: there is no previous/next-line navigation, per-line submit button, or requirement to check one line at a time.
- Compare the full draft to the full expected lyrics continuously as the user edits. Feedback should feel immediate: target under 50 ms for ordinary lyrics and never block input for a long computation. Exact alignment is required while within a documented token/edit-frontier/time budget. Beyond that budget, move work off the main thread and use deterministic anchors/chunks plus progressive refinement; show a localized **checking…** state for regions that are not yet exact and never use approximate output to declare completion. Direct normalized equality for a potentially complete draft must remain exact. Benchmark representative short, long, highly repetitive, totally different, and large-paste cases and document results. Run comparison locally; do not send a network mutation for every keystroke.
- Persist every accepted edit immediately to an IndexedDB recovery buffer in the same browser, then debounce cloud autosave to D1. Lifecycle network flush is best effort, not the only defense against data loss. On reload, if the local recovery buffer is newer than the last server-confirmed version, restore it with an explicit **not yet synced** state and reconcile through the normal version/idempotency contract without overwriting either side silently. Clear recovery data only after confirmed cloud persistence, completion/abandonment, or explicit data deletion.
- Implement the writing surface as a robust plain-text editor, not a visually styled but broken textarea illusion. A native `<textarea>` cannot color individual characters; prefer a mature accessible editor engine with proven plain-text, IME, selection, and undo semantics over hand-rolled raw `contenteditable`; a synchronized input/render layer is acceptable if it passes the same behavior tests. Preserve selection and composition ranges, sanitize paste to plain text, and never allow imported or typed HTML to execute. The data model—not the DOM—is the source of truth for the draft. Disable native spellcheck, autocorrect, predictive replacement, and Grammarly-like browser assistance where web-platform controls allow, because they can reveal answers; document that third-party extensions cannot be fully controlled.
- From `compositionstart` through `compositionend`, never replace, normalize, split, or decorate the composing DOM/range and never autosave intermediate composition text. Defer comparison for that range until composition completes. Feedback spans and omission markers are editor decorations, never document data: exclude them from selection, clipboard text, serialization, spellcheck input, and undo history. Feedback-only updates must not create undo entries.
- Render three judged feedback states inline without revealing missing lyric content, plus a neutral state for content excluded by the active grading options:
  - **Correct:** render the user-entered grapheme in an accessible dark green text token.
  - **Incorrect or extra:** retain readable foreground text and add an amber/yellow translucent highlight plus a distinct underline; never use low-contrast yellow text. A substitution renders the typed grapheme once as incorrect and does not also create a missing marker. An insertion renders the typed grapheme as extra.
  - **Missing:** only a pure deletion gap renders an amber insertion marker at the aligned gap. It must be visually distinct from the real typing caret (for example a short notched bar or bar with a dot), occupy enough width to be discoverable, reveal no missing characters, and expose a concise localized accessible label such as “missing text here.” Collapse a consecutive missing run into one marker rather than a forest of cursors, while retaining its missing-token count for the summary.
  - **Neutral:** punctuation ignored by the active setting uses the normal editor foreground with no success/error styling and is excluded from all correctness counts.
- The palette should borrow Grammarly’s low-distraction inline-annotation discipline without copying its branding. Define semantic design tokens rather than scattering literal colors, support light/dark themes, and meet WCAG contrast requirements. Color is never the only signal: incorrect text also has an underline, missing text has a unique shape, and a nearby localized status summary reports counts for correct, incorrect/extra, and missing grapheme clusters. Do not announce the full status on every keystroke; use a polite, debounced screen-reader summary and announce completion assertively once.
- Alignment and grading are normative. Normalize both values to Unicode NFC. Preserve newline as a distinct semantic token. Normalize horizontal Unicode whitespace runs within each line to one ASCII space and trim trailing horizontal whitespace, but do not collapse or discard line breaks. When case sensitivity is off, apply locale-independent Unicode default case folding. When punctuation sensitivity is off, remove code points in Unicode General Category `P*` from the judged token stream while retaining provenance to render typed punctuation neutrally. Both sensitivity options default off and are fixed for a session. Do not apply compatibility normalization or remove letters, marks, numbers, symbols, emoji, or CJK characters.
- Tokenize using Unicode extended grapheme clusters plus explicit newline tokens, never UTF-16 code units. Exact alignment operations are match, substitute, insert, and delete with documented deterministic costs and tie-breaking; prefer exact matches and stable nearby anchors so one early insertion or omission does not cascade into false errors. Match increments correct, substitute increments incorrect, insert increments extra, and delete increments missing. A substitution never also increments missing. A missing newline produces a missing marker at the line boundary; an extra newline produces an incorrect blank-line/gutter marker. Optional word grouping must never change correctness.
- Maintain provenance from each normalized token back to its original draft grapheme/range. If case folding expands one original grapheme, render it green only when all derived judged tokens match; otherwise render the whole original grapheme amber. All original graphemes in a collapsed horizontal-whitespace run share the resulting match/error state. Ignored punctuation is neutral. Calculate progress using the normalized judged expected-token count as denominator; report correct matches, incorrect substitutions, extras, and missing tokens separately, and document the empty-answer edge case.
- Show unobtrusive live progress without revealing answers. Completion occurs automatically only when exact normalized alignment has no incorrect, extra, or missing tokens; approximate or still-refining regions can never complete a session. Then show a clear completed state and allow the user to review their own correctly completed draft or start again. An explicit **End and reveal lyrics** action requires confirmation, marks the session abandoned, and may then show the answer.
- Allow at most one in-progress session per song. **Start dictation** resumes it; **Start over** requires confirmation and marks the old session abandoned. Refreshing or reopening the same browser profile resumes the saved draft. Record `started_at`, `completed_at`, abandoned state, wall-clock completion duration, and final aggregate counts—never a keystroke history. Show useful completion history on the song detail view and recent activity overview. Do not add gamification, social features, leaderboards, sharing, or AI-generated content.
- Empty songs, blank lyric lines, very long/repeated lines, large paste operations, edits near the beginning of a long draft, emoji, ZWJ sequences, combining characters, apostrophes, CJK punctuation, IME composition, and mixed Chinese/English text must behave predictably and be covered by tests.

### 4. Anonymous identity and cloud sync

- There is no registration, login, email, password, OAuth, or user-visible account system.
- On first server interaction, create a cryptographically random opaque anonymous credential with at least 256 bits of entropy. In production use a host-only cookie named `__Host-ld_identity` with `Path=/`, no `Domain`, `HttpOnly`, `Secure`, `SameSite=Lax`, and a documented 365-day sliding lifetime renewed at most once per day. Use a clearly separate localhost-only cookie/configuration when `Secure` is unavailable.
- Never use a sequential/raw database identifier as authentication. Store only a one-way cryptographic hash of the credential in D1. Use constant-time comparison where relevant. Do not make identity or private records accessible from JavaScript.
- A missing, malformed, expired, or unknown credential must never recover or reveal an earlier identity: create a new identity and return an empty library. Update `last_seen_at` only after successful validation. Purge identities inactive for more than 365 days and all dependent data through a documented, testable scheduled maintenance path. Disclose the retention and identity-loss behavior in both locales.
- Every lyrics, settings, session, and progress query/mutation must derive ownership from the validated cookie on the server. Enforce ownership in the query itself where practical. Never accept a client-supplied owner ID.
- Provide CSRF protection appropriate to the chosen architecture for every state-changing request, validate `Origin`/`Host`, use restrictive CORS and correct content types, and implement a tested CSP, `X-Content-Type-Options: nosniff`, restrictive `Referrer-Policy`, frame protection, and production HSTS. Every private API response and every response that sets identity must use `Cache-Control: no-store` and must not be cached by the CDN. Imported filenames, titles, artists, lyrics, and diffs must render as text, never trusted HTML.
- Choose and document numeric per-route rate limits in one shared configuration; enforce them server-side, return `429` plus `Retry-After`, test boundaries and local/production-equivalent behavior, and do not persist raw IP addresses in logs. Upload and field-size limits are defined in the import section.
- Every mutable record carries a server-generated integer version. Update and delete requests supply the last observed version; a stale request returns stable `409 VERSION_CONFLICT` without mutation, and the UI preserves unsaved input while offering reload/retry. Define an explicit retry contract for song/session creation, draft autosave, session completion/abandonment, song deletion, and delete-all. Operations that create records or increment counts use a credential-scoped idempotency key stored with the result. Delete-all is safe to repeat and must not accidentally create a replacement identity. Test response-loss retries, duplicate concurrent requests, and stale update/delete races.
- Synchronize across tabs and visits that share the cookie. After a successful mutation update the current tab immediately, notify same-origin tabs with `BroadcastChannel` or an equivalent primitive, and revalidate on focus/visibility change; no WebSocket is required. Never show “synced” until the server confirms success.
- Local UI state may be cached for resilience, but D1 is the source of truth for saved content and progress. Clearly distinguish offline/network failure from an empty library and allow safe retry.
- Explain in the UI and privacy documentation that clearing cookies loses access to the anonymous library and that anonymous data does not automatically transfer between browsers/devices.
- Provide a localized privacy/data screen with **Delete all my data**. Require confirmation, delete all owned cloud records transactionally, remove every local recovery/cache/preference record belonging to that identity, expire the identity cookie, and test the full flow. Collect no analytics or telemetry by default.
